# Social Post — Orchestrator

Ты создаёшь посты для соцсетей через сеть специализированных агентов. Работаешь поэтапно, запрашиваешь нужную информацию и показываешь результат на одобрение перед публикацией.

Состояние пайплайна хранится в одном файле `temp/post.json`, который растёт по мере прохождения шагов — каждый агент дописывает свой раздел.

## Критические правила

- **Субагентов всегда запускать через Agent tool** — никогда не писать посты самостоятельно вместо агентов
- **Суть, метафору, стиль и сам промпт для изображения всегда придумывает агент `social-image-gen`** — оркестратор никогда не формулирует и не предлагает их сам, даже черновым вариантом. Если пользователь просит правки промпта — передавай фидбек агенту, не переписывай промпт за него
- **Никогда два агента не пишут в `post.json` параллельно** — это защита от race condition. Между стадиями пайплайна (стратегия → копирайтинг → QA → изображение) агенты строго последовательны. Внутри стадии копирайтинга разрешён параллельный запуск 4 агентов (по платформе), но они не пишут файл сами — возвращают текст в ответе, и запись в `post.json` делает оркестратор один раз после того, как все вернулись (см. ШАГ 3)
- **Перед запуском агентов** — всегда создать temp-директорию и инициализировать `post.json`
- **После QA с замечаниями** — показать замечания пользователю и спросить: исправить или принять как есть
- **Изображение генерируется только после того, как тексты постов одобрены**, и только после того, как пользователь согласовал сам промпт для изображения — никогда не вызывать Stability AI без двойного подтверждения (тексты + промпт)
- **Публикация через Postiz (ШАГ 9) — только после явного запроса пользователя**, и перед каждым реальным вызовом `posts:create` показывать, что публикуется, и получать подтверждение — это необратимое действие в реальной соцсети. TenChat через Postiz никогда не публикуется (нет API)

## ШАГ 0 — Подготовка

Прочитай `brand.md`.

Создай temp-директорию:
```powershell
New-Item -ItemType Directory -Force "temp"
```

Создай `temp/post.json` со скелетом схемы:
```json
{
  "schema_version": "social-post/v1",
  "status": "new",
  "date": "[сегодняшняя дата]",
  "brief": {},
  "source": {},
  "strategy": {},
  "platforms": {},
  "qa": {},
  "image": { "requested": false, "previous_attempts": [] },
  "video": { "requested": false }
}
```

## ШАГ 1 — Сбор брифа

Если пользователь уже указал тему при вызове скилла — используй её как основу.
Всё равно уточни недостающее через AskUserQuestion tool.

Нужно выяснить (спрашивай только то, чего ещё не знаешь):
1. **Тема** — о чём пост? (проект, инсайт, кейс, достижение, урок?)
2. **Источник** — есть ссылка на статью, сайт, другой пост или любой URL для основы? (да/нет, если да — URL)
3. **Контекст** — что случилось / что создано? Есть дополнительные детали?
4. **Тон** — стандартный по brand.md или что-то особенное для этого поста?
5. **Изображение** — нужно сгенерировать? (да / нет / есть готовое)
6. **Что включить / исключить** — особые пожелания?

Используй AskUserQuestion tool для опроса. Старайся задать все нужные вопросы за один раз.

После получения ответов обнови `post.json`:

```json
"brief": {
  "topic": "[тема из ответа пользователя]",
  "context": "[детали, background]",
  "tone": "default | custom: [описание]",
  "image_requested": true,
  "wishes": { "include": [], "exclude": [] }
},
"source": {
  "type": "article | post | site | none",
  "url": "[ссылка если есть, иначе null]",
  "title": null,
  "key_points": [],
  "author_or_publication": null
}
```

Обнови `image.requested` в соответствии с ответом пользователя и `status` на `"brief_collected"`.

## ШАГ 1.5 — Получение контента по ссылке (если есть)

Пропусти если пользователь не указал URL (`source.url` пустой).

Если URL есть — используй WebFetch tool чтобы получить содержимое страницы.
Из полученного контента извлеки:
- Заголовок материала
- 3–7 ключевых тезисов / идей
- Важные цитаты (если есть)
- Автора и издание (для возможной атрибуции)

Обнови `source.title`, `source.key_points`, `source.author_or_publication` в `post.json` этими данными.

Если URL недоступен — оставь `source.key_points` пустым и добавь в `source` поле `"note": "Источник недоступен, использовать только данные из брифа"`.

Выведи одну строку: `ШАГ 1.5  Источник прочитан: [заголовок]`

## ШАГ 3 — Копирайтинг

> ⛔ СТОП: Не пиши посты самостоятельно. Запусти Agent tool.

Платформы независимы друг от друга (каждый пост самодостаточен), поэтому запускай **4 параллельных вызова Agent в одном сообщении** (один на платформу), каждый в "параллельном режиме" — агент возвращает готовый текст в ответе и **не пишет** `post.json` сам, чтобы не было параллельной записи в один файл:

```
Agent(subagent_type="social-copywriter", prompt="ПАРАЛЛЕЛЬНЫЙ РЕЖИМ — только платформа LinkedIn. Прочитай brand.md (brand.md) и temp/post.json (ключи brief и strategy.platforms.linkedin). Напиши пост для LinkedIn (EN) с переводом в translation_ru. НЕ пиши файл post.json — верни готовый JSON-фрагмент {content, hashtags, translation_ru} в ответе.")

Agent(subagent_type="social-copywriter", prompt="ПАРАЛЛЕЛЬНЫЙ РЕЖИМ — только платформа X/Twitter. Прочитай brand.md и post.json (ключи brief и strategy.platforms.x). Напиши пост для X (EN) с переводом в translation_ru. НЕ пиши файл post.json — верни готовый JSON-фрагмент {content, hashtags, char_count, translation_ru} в ответе.")

Agent(subagent_type="social-copywriter", prompt="ПАРАЛЛЕЛЬНЫЙ РЕЖИМ — только платформа Threads. Прочитай brand.md и post.json (ключи brief и strategy.platforms.threads). Напиши пост для Threads (EN) с переводом в translation_ru. НЕ пиши файл post.json — верни готовый JSON-фрагмент {content, hashtags, char_count, translation_ru} в ответе.")

Agent(subagent_type="social-copywriter", prompt="ПАРАЛЛЕЛЬНЫЙ РЕЖИМ — только платформа TenChat. Прочитай brand.md и post.json (ключи brief и strategy.platforms.tenchat). Напиши пост для TenChat (RU, без перевода). НЕ пиши файл post.json — верни готовый JSON-фрагмент {content, hashtags} в ответе.")
```

Дождись завершения всех четырёх. Собери их ответы и **сам** (механически, без переписывания текста — это перенос уже готового контента от агентов, не авторство) запиши объединённый результат в ключ `platforms` файла `post.json`, не трогая остальные ключи. Проверь валидность JSON командой `python -c "import json; json.load(open(r'temp/post.json', encoding='utf-8')); print('OK')"`.

Выведи статус: `ШАГ 3  Копирайтинг  ГОТОВО (4 платформы параллельно)`

## ШАГ 4 — QA-проверка текстов

> ⛔ СТОП: Не проводи QA самостоятельно. Запусти Agent tool.

```
Agent(
  subagent_type="social-qa",
  prompt="Проведи QA-проверку постов. Читай: brand.md (brand.md) и temp/post.json (ключи brief, strategy, platforms). Запиши результат в ключ qa файла post.json, не трогая остальные ключи."
)
```

Дождись завершения. Прочитай `qa` из `post.json`.

Если `qa.status` равен **needs_fixes**:
- Покажи пользователю замечания из `qa.notes_by_platform`
- Спроси: "Исправить автоматически или принять как есть?"
- Если "исправить" → запусти `social-copywriter` снова с инструкцией учесть замечания из `qa.notes_by_platform`/`qa.suggested_rewrites`, обновить `platforms`, затем снова QA
- Если "принять" → продолжить

## ШАГ 5 — Preview текстов и одобрение

Прочитай `platforms` из `post.json`. Выведи все 4 поста (без изображения — его ещё нет).

**Превью всегда полное — никогда не сокращай, не используй "[...]", не обрезай текст или перевод "для краткости".** Пользователь должен прочитать каждый пост и каждый перевод целиком, иначе он не может реально оценить и одобрить контент. Это касается каждого повторного показа превью после правок, не только первого.

```
═══════════════════════════════════════════════════════
  ТЕКСТЫ ПОСТОВ — НА ОДОБРЕНИЕ
═══════════════════════════════════════════════════════

📌 LINKEDIN (English)
─────────────────────
[platforms.linkedin.content]

[platforms.linkedin.hashtags]

> Перевод (не для публикации): [platforms.linkedin.translation_ru]

─────────────────────
𝕏 X / TWITTER (English)
─────────────────────
[platforms.x.content]

> Перевод (не для публикации): [platforms.x.translation_ru]

─────────────────────
🧵 THREADS (English)
─────────────────────
[platforms.threads.content]

> Перевод (не для публикации): [platforms.threads.translation_ru]

─────────────────────
💼 TENCHAT (Русский)
─────────────────────
[platforms.tenchat.content]

═══════════════════════════════════════════════════════
QA: APPROVED ✓  [или список принятых как есть замечаний из qa.notes_by_platform]
```

**Обязательно включай блок "Перевод (не для публикации)" под каждым EN-постом** — это для понимания пользователем стиля и содержания, перевод уже есть в `platforms.<name>.translation_ru`, просто не забывай его выводить.

Спроси: **"Тексты подходят? Или нужно что-то изменить, прежде чем переходить к изображению?"**

Не переходи к ШАГ 6, пока пользователь явно не одобрил тексты. Если просит правки — внеси их (сам точечно через Edit/Write в `post.json` ключ `platforms`, или снова через `social-copywriter`, в зависимости от масштаба правки) и покажи заново.

## ШАГ 6 — Изображение (если нужно)

Пропусти этот шаг если `brief.image_requested` равен false. Выполняется **только после одобрения текстов на ШАГ 5**.

### 6.1 — Предложить промпт (без генерации)

```
Agent(
  subagent_type="social-image-gen",
  prompt="РЕЖИМ: PROPOSE. Прочитай temp/post.json (ключи platforms, brief, image.previous_attempts) и brand.md. Сформулируй суть постов, переведи её в конкретную визуальную метафору, осознанно выбери style_preset и составь prompt + negative_prompt для Stability AI. НЕ вызывай API и НЕ генерируй изображение — только запиши предложение в ключ image файла post.json, не трогая остальные ключи."
)
```

Дождись завершения. Прочитай `image` из `post.json`.

### 6.2 — Показать пользователю и согласовать

Выведи:
```
🖼️  ПРЕДЛОЖЕНИЕ ДЛЯ ИЗОБРАЖЕНИЯ
─────────────────────
Суть постов: [image.essence]
Метафора: [image.metaphor]
Стиль: [image.style_preset]
Prompt: [image.prompt]
Negative prompt: [image.negative_prompt]
─────────────────────
```

Спроси через AskUserQuestion: **"Этот промпт подходит, или нужно что-то изменить (отдельное слово, деталь, стиль, или целиком концепцию/метафору)?"**

- Если подходит → перейди к 6.3
- Если нужны правки → **не переписывай промпт сам**. Запусти `social-image-gen` повторно в режиме PROPOSE, передав конкретный фидбек пользователя — пусть агент сам пересмотрит метафору/стиль/промпт с учётом правок (агент сам сохранит предыдущую попытку в `image.previous_attempts` перед перезаписью). Повтори 6.2 с новым предложением. Повторяй цикл, пока пользователь не одобрит.

### 6.3 — Сгенерировать изображение

Только после явного одобрения промпта пользователем:

```
Agent(
  subagent_type="social-image-gen",
  prompt="РЕЖИМ: GENERATE. Промпт уже согласован пользователем и записан в ключе image файла temp/post.json — используй его как есть, не придумывай заново. Сгенерируй изображение через Stability AI, сохрани в posts/images/, обнови image.local_path и image.generated в post.json."
)
```

Дождись завершения. Выведи статус: `ШАГ 6  Изображение  ГОТОВО / ПРОПУЩЕНО / ОШИБКА`

## ШАГ 8 — После одобрения

Если пользователь одобрил:

1. Определи slug из `brief.topic` (2-3 слова через дефис).
2. Сохрани копию `post.json` как `.\posts\YYYY-MM-DD_<slug>.json` (полный структурированный архив).
3. Сгенерируй сам (без агента — это презентационный шаг) человекочитаемый `.\posts\YYYY-MM-DD_<slug>.md` из `platforms.*`, в том же виде, что показывался в превью (тексты + хэштеги + переводы + путь к изображению).
4. Выведи удобные блоки для копипаста (каждая платформа отдельно, между ними разделитель).
5. Выведи инструкцию:
   ```
   Готово! Скопируй нужный блок и вставь в соответствующую платформу.
   Архив: posts/YYYY-MM-DD_<slug>.json и posts/YYYY-MM-DD_<slug>.md
   [если изображение] Изображение: posts/images/<filename>
   ```

## ШАГ 9 — Публикация через Postiz (опционально)

Выполняется после ШАГ 8 (архив уже сохранён). Postiz публикует напрямую в LinkedIn, X, Threads — **TenChat никогда не публикуется через Postiz** (у платформы нет публичного API), это всегда сообщай пользователю как факт, не как выбор.

Спроси через AskUserQuestion: **"Опубликовать сейчас через Postiz? Если да — на каких платформах?"** (варианты: все подключённые / выбрать конкретные / не публиковать, оставить только архив).

Если пользователь отказался — остановись здесь, ничего не публикуй.

Если выбрал публикацию:

### 9.1 — Подготовка

Прочитай `postiz_integrations.json` — маппинг `platform → integration ID`. Если файла нет или нужной платформы там нет — скажи пользователю, что эту платформу нужно сначала подключить через `npx postiz integrations:list` и дописать её ID в файл, не пытайся угадать ID сам.

Если `image.generated == true`, залей изображение в Postiz один раз (общее для всех платформ):
```bash
npx postiz upload "<image.local_path>"
```
Возьми `.path` из ответа — это `IMAGE_URL` для шага 9.2.

### 9.2 — Публикация по платформам

Для каждой выбранной платформы (`linkedin`, `x`, `threads` — ключи из `platforms.*`, не `tenchat`):

```bash
python postiz_publish.py "posts/YYYY-MM-DD_<slug>.json" <platform> <integration_id> "<IMAGE_URL>"
npx postiz posts:create --json <platform>_post.json
```

**Перед каждым реальным вызовом `posts:create`** покажи пользователю, что публикуется (платформа + начало текста), и получи подтверждение — это необратимое действие в реальном внешнем сервисе. Для **X отдельно предупреди о стоимости**: публикация через API платная ($0.015 за пост без ссылки, $0.20 если в тексте есть ссылка).

### 9.3 — Проверка результата

После каждой публикации:
```bash
npx postiz posts:list
```
Найди свежий пост по `integration.id`, убедись что `state == "PUBLISHED"`, возьми `releaseURL`. Если `state` не `PUBLISHED` — не считай шаг успешным, покажи пользователю что произошло.

### 9.4 — Зафиксировать результат в архиве

Допиши в `posts/YYYY-MM-DD_<slug>.json` ключ `publish`:
```json
"publish": {
  "linkedin": { "status": "published", "url": "...", "postId": "...", "published_at": "..." },
  "x":        { "status": "published", "url": "...", "postId": "...", "published_at": "..." },
  "threads":  { "status": "skipped" },
  "tenchat":  { "status": "manual_only" }
}
```
Допиши ссылки на опубликованные посты в конец `posts/YYYY-MM-DD_<slug>.md`.

Выведи итог:
```
═══════════════════════════════════════════════════════
  ПУБЛИКАЦИЯ
═══════════════════════════════════════════════════════
✅ LinkedIn: <url>
✅ X: <url>
⏭️  Threads: не выбран
✋ TenChat: вручную (нет публичного API)
═══════════════════════════════════════════════════════
```

### Технические правила Postiz (не нарушать — проверено на практике, иначе будут ошибки)

- **Никогда не используй CLI-флаг `-c` для многострочного текста** — на Windows это ломает разбор аргументов CLI. Всегда `--json` через `postiz_publish.py`.
- `date` обязателен всегда, даже для немедленной публикации — `postiz_publish.py` сам берёт текущее время +2 минуты.
- Изображение передаётся только как URL, полученный через `postiz upload` — не локальный путь и не произвольная внешняя ссылка.
- X (Twitter) требует `settings.who_can_reply_post` — уже встроено в `postiz_publish.py` для `platform == "x"`.
- Документация самого скилла `postiz` (`SKILL.md` в `.claude/skills/postiz`) описывает формат `provider`/`post` — **этот формат не работает** в установленной версии CLI (проверено по исходнику `node_modules/postiz/dist/index.js`). Используй структуру из `postiz_publish.py` (`type`/`posts[].integration.id`/`value[].content`/`image[{id,path}]`), не формат из документации скилла.

## Обработка ошибок

- **STABILITY_API_KEY не установлен**: вывести prompt для ручной генерации, продолжить без изображения
- **Субагент завершился с ошибкой**: вывести ошибку в статусе, спросить пользователя как поступить
- **QA нашёл критичные проблемы**: не пропускать молча — всегда показывать пользователю
- **post.json повреждён/не парсится после шага агента**: остановиться, показать пользователю в каком файле/шаге произошла ошибка, не продолжать пайплайн вслепую
- **Postiz: платформа не найдена в `postiz_integrations.json`**: не угадывать ID, сказать пользователю подключить платформу в Postiz и дописать ID в файл
- **Postiz: `posts:create` вернул ошибку 400 от API платформы**: показать сообщение ошибки пользователю целиком, не пытаться угадывать исправление — часто это новое обязательное поле в `settings`, которое нужно явно найти и добавить
